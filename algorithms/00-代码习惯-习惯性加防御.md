# 代码习惯：习惯性加防御

> 一个反复出现的个人习惯，**已记录 5 次**。不是 bug，但会影响别人对你代码的判断。
> ✅ **2026-11-14 更新：第 6 次（无重复子串）主动改掉了，见文末「好转记录」。**

---

## 现象

写代码时，会**条件反射地加一些"看起来必要"的保护**：

```java
// 1. 开头加长度判断
if (nums.length == 0 || nums.length == 1) return;

// 2. 循环里加永远不会成立的 break
if (right >= nums.length) break;

// 3. 把边界人为缩一格
while (left < nums.length - 1 && ...)

// 4. 用 else if 写一个必然成立的条件
else if (height[left] > height[right])
```

**这些都不影响正确性，但都不是必需的。**

---

## 已经出现的 4 次

### ① 移动零：`if (nums.length == 0 || nums.length == 1) return;`

```java
if (nums.length == 0 || nums.length == 1) return;   // 多余
```

**不需要**。`while(left < right)` / `while(right < nums.length)` 自己处理了。
`[0]` 时 `right = 1`，`while(1 < 1)` 直接 false，什么都不做，返回原数组。**完全正确。**

### ② 移动零：`if (right >= nums.length) break;`

```java
while (nums[right] == 0 && right < nums.length - 1) right++;
if (right >= nums.length) break;    // ← 死代码
```

`right` 被内层 `while` 的 `right < nums.length - 1` 卡住，**最大只能是 `length - 1`**，永远不可能 `>= length`。

**这行永远不执行。**

### ③ 移动零：把边界人为缩一格

```java
while (nums[left] != 0 && left < nums.length - 1)   // 本应 < nums.length
```

为了「不越界」而写 `length - 1`。代价是：
**判定顺序反了**（先取值 `nums[left]`，后判边界），而且读代码的人要多想「为什么少一格」。

### ④ 盛最多水：`if (height.length == 0 || height.length == 1) return 0;`

```java
if (height.length == 0 || height.length == 1) return 0;   // 多余
```

**不需要**。

| 长度 | left | right | `while(left<right)` |
|---|---|---|---|
| 0 | 0 | **-1** | `0 < -1` → false，返回 0 |
| 1 | 0 | 0 | `0 < 0` → false，返回 0 |

`while(left < right)` 本身就是最自然的边界保护。

### ⑤ 无重复字符的最长子串：`while (fast < s.length() - 2)`

```java
while (fast < s.length() - 2)      // 本应 < s.length()
```

**少写了 2 格**，后果：

| s | length | 循环实际跑几次 | 结果 |
|---|---|---|---|
| `"abc"` | 3 | 1 次 | **index 0 从没处理过** |
| `"ab"` | 2 | **0 次** | 返回 0（答案应为 2） |

**这是"缩边界"最典型的形态**：想不清楚边界在哪，就往后缩一点"求安全"。

### 一个规律

**5 次里有 3 次是「缩边界」**：

```
length - 1、length - 1、length - 2
```

**缩边界不会让它变对，只会让它静默地少处理几个元素**——比越界崩溃更难发现。

> **边界写错就该让它崩，崩了才知道错在哪。缩边界只会把 bug 藏起来。**

---

## 为什么这是问题

### 1. 会掩盖真正需要处理的特殊情况

一个多余的 `if (length <= 1) return`，会让读代码的人以为：**"这里肯定有特殊情况，我得想想是什么。"**

结果想了半天，发现什么都不处理也一样对。**白花时间，还降低了信任。**

### 2. 真正的问题被"防御"掩盖

移动零里，为了不越界写成 `length - 1`，结果**判定顺序反了**。表面上"更安全了"，实际上引入了新隐患：**哪天有人把 `-1` 去掉，立刻崩。**

**过度防御和漏判边界，是同一个问题的两面：都没想清楚"真正的边界在哪"。**

### 3. 面试官会注意

面试看代码时，最先注意到的不是算法，是这几样：

| 面试官看到 | 判断 |
|---|---|
| 死代码（永不执行的 `break`） | "他自己没跑过这条路径" |
| 多余的 guard | "他在猜边界，而不是推导边界" |
| 人为缩一格的边界 | "他知道会越界，但没想清楚为什么" |

**这三样都会降低"代码是思考出来的"这个印象。**

---

## 怎么自查：删一行测试

**对每一个 guard、每一个提前 return、每一个 `break`，问一句：**

> **删掉它，代码还对吗？**
> **对 → 它是多余的，删掉。**
> **不对 → 它是有用的，但要在注释里写清为什么。**

以盛水这题为例：

```
删掉 if (height.length <= 1) return 0;
剩下 while(left < right) 能处理 length=0 和 length=1 吗？
→ 能，left 和 right 初始化后循环条件直接 false
→ 结论：多余，删
```

### 第二个自查：这条路径跑得通吗

**对每一个 `break` 和 `if`，问一句：**

> **什么输入能让这个条件成立？举一个具体例子。**

举不出来 → **就是死代码**。

移动零里那个 `if (right >= nums.length) break`，你举不出任何输入能让它成立——因为 `right` 被内层条件卡在 `length-1`。

---

## 什么时候**该**加防御

不是所有 guard 都多余。**该加的情况只有一种：后面的代码会直接访问可能越界的位置，且前面的循环没兜住。**

```java
// ✅ 该加：这里要先访问 nums[0]，但还不确定长度
if (nums.length == 0) return result;
if (nums[0] > 0) break;

// ❌ 不该加：while 条件自己就能兜住
if (nums.length <= 1) return;
while (left < right) { ... }
```

**判断标准：这个 guard 是"循环兜不住"还是"我不确定循环兜不兜得住"？**

- 前者 → 加
- 后者 → **先去推导循环，别加**

---

## 正确的"防越界"姿势

这三次的教训指向同一个结论：

> **边界判断要写在取值之前，而且只写在真正需要的地方。**

```java
// ❌ 先取值，后判边界（靠运气不崩）
while (nums[left] != 0 && left < nums.length - 1)

// ✅ 先判边界，再取值
while (left < nums.length && nums[left] != 0)
```

**顺序反了，只要边界值写错一格就崩。顺序对了，边界写宽写窄都只会逻辑错，不会崩。**

---

## 更好的解法：让边界问题消失

移动零的两个版本对比很说明问题：

| 写法 | 需要几处边界判断 |
|---|---|
| 手动「找零 → 找非零 → 交换」 | **3 处**（容易漏） |
| 「收集非零 + 补零」 | **0 处**（`for` 循环天然有界） |

**不是"把边界判断写对"，而是"换一个不需要边界判断的结构"。**

> 遇到「原地移动/删除元素」，先问：我是要**把 A 移到 B**，还是**把 C 收集起来**？
> 前者要追踪两个位置，处处防越界；后者只要一个写指针。

---

## 一条规则总结

> **先推导边界在哪，再决定要不要写判断。**
> **写完后删一行测试：删掉还对，就是多余的。**

**不要用 guard 代替推导。** 防御性代码只能防"没想到"，不能防"没想清楚"。

# 第二类问题：复制粘贴没改全

> 2026-11-14 新增。和「习惯性加防御」不同——这类问题**编译通过、逻辑自洽，但结果恒错**。

---

## 现象

写两个相似的循环或判断时，**复制上一段，只改了一半**。

```java
for (char c : a.toCharArray()) cnt[c - 'a']++;
for (char c : a.toCharArray()) cnt[c - 'a']--;   // ❌ 应该是 b
```

同一个字符串加了又减 → `cnt` 恒为全 0 → 判断函数**对任何输入都返回 true**。

---

## 用 `aab` / `abb` 看后果

### 出错的版本（字母异位词 0438 v2）

```java
boolean findEXWord(String a, String b) {
    int[] cnt = new int[26];
    for (char c : a.toCharArray()) cnt[c - 'a']++;
    for (char c : a.toCharArray()) cnt[c - 'a']--;   // ← 复制忘了改 b
    for (int x : cnt) if (x != 0) return false;
    return true;
}
```

**结果**：`"aab"` 和 `"abb"` 判断为**是异位词**（实际不是）。

### 更直观的例子

`s = "ab"`, `p = "b"`：

| index | sub | 判断 | 结果 |
|---|---|---|---|
| 0 | `"a"` | 恒 true | 加入 0 ❌ |
| 1 | `"b"` | 恒 true | 加入 1 ✅ |

**输出 `[0, 1]`，正确答案只有 `[1]`。**

`"a"` 和 `"b"` 根本不是异位词，却通过了判断。

---

## 为什么这类 bug 特别难发现

| 特点 | 说明 |
|---|---|
| **编译通过** | 类型、语法全对 |
| **逻辑自洽** | 代码"看起来"就是在做加减 |
| **不崩** | 不抛异常，只是结果错 |
| **输出有规律** | 往往返回全部 / 返回空，容易误以为"边界问题" |

**靠"读一遍"几乎发现不了**——因为读的时候会下意识跳过重复的循环头。

---

## 自查方法

### ① 看循环头是不是复制来的

```java
for (char c : a.toCharArray()) {}    // 第一段
for (char c : a.toCharArray()) {}    // 第二段 ← 变量名一模一样？
```

**只要是复制出来的，逐个对变量名。**

### ② 用"极端输入"测

| 输入 | 期望 | 如果是 bug 会怎样 |
|---|---|---|
| 两个**完全不同**的串（`"a"` vs `"b"`） | false | **返回 true** |
| 两个**长度不同**的串 | false | 可能崩，也可能 true |

**第一个用例就能戳穿**：如果"完全不同"都判 true，那判断逻辑一定失效了。

**规则：写完一个判断函数，立刻用"必然为 false"的输入测一次。** 全 true 的 bug 一秒就能发现。

### ③ 别只测"应该通过"的用例

v2 提交时大概率只测了正确的情况（`s="cbaebabacd"` 有没有返回 `[0,6]`），但没测"不该通过"的情况。

> **判断型函数，至少有 2 个测试用例：一个应该返回 true，一个应该返回 false。**

---

## 这一类的常见变体

| 变体 | 例子 |
|---|---|
| 循环变量没改 | `for (c : a) ...` 复制后还是 `a` |
| 下标没改 | `arr[i]` 复制后还是 `i`，应该是 `j` |
| 条件没改 | `if (x > 0)` 复制后还是 `> 0`，应该是 `>= 0` |
| 方法参数顺序反了 | `isSame(need, window)` 复制后没换回来（这题其实不影响，但要养成核对习惯） |

---

## 和三件事的关系

### 和「删一行测试」同源

- **删一行测试**检查的是「多余的代码」
- **对变量名**检查的是「错的代码」

两个动作都靠「**逐行质疑自己刚才写的**」，不是靠通读。

### 和 IDE 的关系

**IDE 不会警告**：两个循环都合法，编译器不知道你想遍历 `b`。

**唯一能防的是习惯**：复制之后，**立刻改、立刻对**，不要"等会儿再改"。

### 和面试的关系

面试手写代码时**尤其容易犯**——因为紧张、时间紧、想着赶紧写完。

> **面试时写完一个方法，花 10 秒扫一遍变量名，比多写 5 分钟有用。**

---

## 两条规则

> **① 复制出来的代码，先改全变量，再往下写。**
> **② 判断型函数，必须有「应该返回 false」的测试用例。**

第二类问题不像第一类那样"只是不好看"——**它会直接让答案全错**。

2. **写完做「删一行测试」**

> **习惯是能改的。** 但改的方式不是"记住别写"，而是**换一个判断动作**：从"要不要加保护"变成"删掉还对吗"。
